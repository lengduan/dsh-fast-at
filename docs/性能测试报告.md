# @ 输入性能测试报告

> 本文件是**落地报告**，不是会话记录。每次场景测量完成后立即追加，
> 保证数据可离线查阅、可追溯，不依赖会话上下文。

## 测量方法（唯一可信口径）

> 本报告有两种口径，**不可混用**：
> - **A–D** 测「长按按键 15 次的每键主线程成本」，判定是否积压（下面这段）。
> - **E** 测「按下 `@` 到候选行出现」的墙钟耗时，判定菜单快慢（见场景 E 开头）。

```js
// 1. 严格清空并断言（execCommand('delete') 对 Lexical 无效，必须断言）
for (let k = 0; k < 4; k++) {
  await press('Control+a'); await press('Delete');
  if (innerText.length === 0) break;   // 不断言 = 数据作废
}

// 2. 连续输入 15 键，间隔 16ms，扣除等待得每键主线程成本
const t0 = performance.now();
for (let i = 0; i < 15; i++) { document.execCommand('insertText', false, ch); await sleep(16) }
const perKey = (performance.now() - t0 - 14 * 16) / 15;

// 3. 断言 innerText.length === 15，否则本轮数据无效
```

**判定标准**：OS 按键重复速率约 **33ms/键**。`perKey < 33ms` = 不积压（用户感知流畅）；`> 33ms` = 积压（感知为卡）。

**环境**：Edge 153 headless，视口 1600×900，`freezeAnimations: true`。

## 场景 B：源码含补丁 + 仅保留 deep-ptc / browser-e2e，其余插件全部禁用

**配置**

被禁用的 13 个插件：`ui-skin-815`、`usage-stats`、`quiet-spawn`、`running-session-expander`、

`session-cleanup`、`ds-harness-remote`、`ui-plugin-manager-update-check`、`fast-at`。

**测量结果**（各轮严格清空并断言 len===0）

| 轮次 | 长按 @ ×15 | 插入 | 长按 z ×15 | 插入 |
|---|---|---|---|---|
| 1 | 25.2 ms | 15/15 | 4.6 ms | 15/15 |
| 2 | 35.4 ms | 15/15 | 4.6 ms | 15/15 |
| 3 | 30.2 ms | 15/15 | — | — |
| **中位** | **30.2 ms** | 15/15 | **4.6 ms** | 15/15 |

**关键发现**

| 对比项 | 场景 A | 场景 B | 变化 |
|---|---|---|---|
| 长按 **z** | 23.0 ms | **4.6 ms** | **↓ 5.0×（-80%）** |
| 长按 **@** | 23.0 ms | **30.2 ms** | **≈ 不变（甚至略升）** |

**解读**：

1. **其余插件确实在拖慢普通字符输入** —— 禁用后 `z` 从 23ms 掉到 4.6ms，改善 5 倍。
2. **但它们不是 `@` 的瓶颈** —— `@` 禁用前后基本不变（23ms vs 30ms，属噪声范围）。
3. **`@` 与 `z` 的差距被拉开了**：场景 A 是 1:1，场景 B 是 **6.6:1**（30.2 vs 4.6）。
4. 这说明剥离插件后，`@` 自身路径的成本暴露出来了 —— 之前被插件的整体开销掩盖。
5. `@` 的 30.2ms 仍 < 33ms 节拍，**不积压**，但已接近临界值。

> 注意：场景 B 的 `@` 菜单是 **0 行**（连续 `@` 后查询为 `@@@...`，无候选），
> 与场景 A 的 0 行一致，两者可比。

## 场景 D：纯净源码 + 重新启用 dsh-fast-at

**配置**：纯净 asar（无补丁）+ better-sidebar 禁用 + 其余插件禁用 + **仅启用 dsh-fast-at**

**测量结果**

| 轮次 | 长按 @ ×15 | 长按 z ×15 |
|---|---|---|
| 1 | 12.3 ms | 4.3 ms |
| 2 | 10.2 ms | 4.1 ms |
| 3 | 5.5 ms | — |
| **中位** | **10.2 ms** | **4.3 ms** |

### 最关键的发现：fast-at 比源码补丁更有效

| 对比 | @ | z |
|---|---|---|
| C（纯净，无 fast-at） | 42.8 ms | 12.4 ms |
| D（纯净 + fast-at） | **10.2 ms** | **4.3 ms** |
| **fast-at 贡献** | **↓ 32.6 ms（-76%）** | **↓ 8.1 ms（-65%）** |

**启用 fast-at 后 `@` 从 42.8ms 降到 10.2ms，比源码补丁的效果（42.8→30.2）大得多。**

而且 `z` 也从 12.4ms 降到 4.3ms —— 说明 fast-at 的收益不只是「少发请求」，
它让整个输入路径都变轻了（更少的 React 状态更新 / 更少的重渲染）。

### 同页精确 A/B（用插件自带的 `__FAST_AT_OFF` 开关）

插件源码提供了运行时开关（`dsh-fast-at/lib/client.js`）：

> `__FAST_AT_OFF` 置 true 时包装函数直接转调**原实现**，等价于没装插件。

同一页面、同一时刻、只切换该开关：

| 条件 | @ ×15 | z ×15 |
|---|---|---|
| 插件 **ON** | 4.6 / 8.4 ms | 5.4 ms |
| 插件 **OFF**（原生基线） | 22.1 / 19.6 ms | 3.8 ms |
| **差异** | **慢 3–4 倍** | 无差异 |

**这是最干净的证据**：无需重启、无环境差异，唯一变量就是插件是否接管 `candidates`。

- `@` 路径：插件带来 **3–4 倍** 加速（22ms → 6ms）
- `z` 路径：插件无副作用（5.4 vs 3.8ms，在噪声内）

### 请求验证

启用 fast-at 后 15 次按 `@` 期间的请求：45 条，全部是 `api/fileReferences/list`，
**未出现 `sessionReferenceResolver/candidates`** —— 会话候选确实被本地快照接管。

## 结论汇总（回答 A12）

### 问题 1：源码补丁对 @ 有多少影响？

**答**：有效，但**不是最大因素**。

| 对比（唯一变量 = asar） | @ | z |
|---|---|---|
| B 有补丁 | 30.2 ms | 4.6 ms |
| C 纯净 | 42.8 ms | 12.4 ms |
| **补丁贡献** | **-12.6 ms（-29%）** | **-7.8 ms（-63%）** |

补丁把 `@` 从「积压」（42.8ms > 33ms）拉回「不积压」（30.2ms），但余量只有 3ms。

### 问题 2：其他插件对 @ 有多少影响？

**答**：**影响最大，是唯一能让 @ 从「可接受」变成「明显卡顿」的因素。**

| 对比（唯一变量 = 插件） | @ | z |
|---|---|---|
| better-sidebar **启用** | **63–95 ms** | 11–15 ms |
| better-sidebar **禁用** | 13–31 ms | 4–19 ms |
| **影响** | **慢 4–8 倍** | 约 1 倍 |

以及其余 13 个插件：

| 对比（场景 A vs B，唯一变量 = 13 个插件） | @ | z |
|---|---|---|
| A 全部启用 | 23.0 ms | 未测 |
| B 全部禁用 | 30.2 ms | 4.6 ms |
| **影响** | 差异在噪声内 | 未测 |

**其余插件主要拖慢普通字符输入，不是 `@` 的瓶颈。**

### 问题 3：哪个配置最快？

```
纯净源码 + 仅 fast-at + better-sidebar 禁用  →  @ 10.2 ms   z 4.3 ms
```

**这是所有测过的配置里最好的结果**，比「有补丁 + 全插件」（23ms）快 2.3 倍。

### 由此可得的行动建议

| 优先级 | 行动 | 预期收益 |
|---|---|---|
| P0 | 保持 better-sidebar 禁用 | @ -50ms 以上（最重要） |
| P1 | 保持 dsh-fast-at 启用 | @ -32ms |
| P2 | 其余 13 个插件按需启用 | 主要影响普通字符（z 4.6→23ms），对 @ 影响小 |
| P3 | 源码补丁 A/B | @ -12.6ms，可选；不打也能达标（42.8→有 fast-at 时 10.2） |

> **重要修正**：此前认为「必须打源码补丁」。实测推翻 —— 在纯净源码下，
> 只要 better-sidebar 禁用 + fast-at 启用，@ 就是 10.2ms，**完全达标**。
> 源码补丁的价值是在「不开 fast-at」时的兜底。

## 场景 E：@ 菜单变慢的根因（2026-11-25 追查，2026-11-27 补证 + 重测）

口径：本节所有耗时都量的是**从按下 `@` 到候选行真正出现在界面上**（`role="option"` 由 0 变非空），
不是 RPC 往返、也不是菜单容器出现的时间。

### 症状

用户报告「`@` 内容搜索速度又退化了，非常的严重」。2026-11-25 初次实测：

```
开菜单到候选行出现：42ms / 44ms / 47ms / 63ms  ← 正常
                    1196ms / 1209ms / 1220ms / 1327ms  ← 退化
```

当时判定为「每几次出现一次尖峰」。**2026-11-27 重测推翻了这个定性**，见下文「重测」。

### 追查路线（含错误方向）

| 步骤 | 假设 | 结果 |
|---|---|---|
| 1 | `window.__FAST_AT_OFF` 未定义 ⇒ fast-at 未加载 | **错**。这些变量是读取判断用，本来就 undefined。查插件资源确认 `dsh-fast-at/client.js` 已加载 |
| 2 | 插件补丁未生效 ⇒ 未注册 | **错**。注册走包自带的 bundle 补丁（`insert` 方式），package.json 中 bundles 与 dependencies 均正常 |
| 3 | 索引每 30 秒过期（`INDEX_TTL_MS = 30_000`）⇒ 周期性重建 | **部分对但非主因**。周期对不上 |
| 4 | 直连 `/fast-at/api/sessions.list` 测索引端点 | **排除**。3.9–8.9ms，`stale:false` 后稳定 |
| 5 | **fetch tap 抓 `@` 期间全部请求** | **命中** |

### 根因（fetch tap 直接证据）

一次 1319ms 的 `@` 期间，网络请求如下：

| 请求 | 耗时 | 判定 |
|---|---|---|
| `ds-harness-remote/settings.get` | **1270.6 ms** | 元凶 |
| `api/fileReferences/list` | **1248.8 ms** | 被同时拖慢 |
| `/fast-at/api/sessions.list` | 26.8 ms | 正常 |
| `ds-harness-remote/devices` | 8.5 ms | 正常 |

`ds-harness-remote` 的 `settings.get` 把事件循环占住，同窗口的 `fileReferences/list` 被一起拖慢。

### 重测（2026-11-27，运行时启停对照）

上面的定性只说对了一半。把 `ds-harness-remote` 在运行时启用/禁用（`plugin_manager set_plugin`，
无需重启宿主），用同一套流程各测 5 次，每次先逐字符清空输入框、确认查询是干净的单个 `@`：

| 条件 | 菜单出现耗时（5 次） | 候选行数 | 中位数 |
|---|---|---|---|
| remote 启用 | 1806.1 / 2012.4 / 2376.5 / 1687.8 / 1775.8 ms | 28 | **1806 ms** |
| remote 禁用 | 178.9 / 175.7 / 225.4 / 161.4 / 210.3 ms | 28 | **179 ms** |

**两组候选行数完全相同（都是 28 行），唯一变量就是 remote 的启停。差 10 倍。**

由此修正两点：

1. **不是「偶发尖峰」，是每次必慢。** 启用状态下 5 次全部落在 1.69–2.38 秒，
   没有一次接近禁用态的 180ms。之前看到的「42ms 正常值」出现在 remote 未生效的窗口里。
2. 禁用后残余的 ~180ms 是菜单本身的固有开销（取候选、渲染、逐源 settle），不是缺陷。

### 它会阻塞其他请求，而且会随并发叠加

单看一次 `settings.get` 是 ~1.1 秒。它在宿主侧是**串行**执行的，并发请求会排队：

| 同时在飞的 `settings.get` 数 | 期间一次 fast-at 请求的耗时 |
|---|---|
| 1 | 7.1 ms |
| 2 | 5.5 ms |
| 4 | **2797.3 ms** |
| 8 | **9827.5 ms** |

k=1、k=2 时还没进队列，所以不受影响；从 k=4 起线性放大，8 个并发约 9.8 秒。
**用户连按几次 `@`、或多处同时取设置，延迟会叠加，不是恒定 1 秒。**

这也解释了「两个请求同时出现且都很慢」：它们是并发发出的，同时被同一个慢调用拖住。

### 代码级补证

`ds-harness-remote@0.6.8/dist/client.js:7930-7946` 注册了一个 `trigger: '@'` 的源（`name: '主机'`，`order: -20`）：

```js
candidates: async (_session, request) => {
  if ((await control('settings.get').catch(() => {}))?.config?.remoteTools?.enabled === false) return []
  let devices = await control('devices').catch(() => [])
  ...
}
```

它的 `candidates`（`:7935`）**第一行就 `await control('settings.get')`**，这是每次 `@` 都要付的固定开销。

各源的聚合是**并发**的，不是串行排队 —— `@deepseek-ai/dsh-client-ui-input-trigger/lib/client.js:25704`：

```js
for (const source of roster)
  source.candidates(projection, {...}).then(...)   // 循环里没有 await
```

菜单按源逐个 settle（同文件 `:15625` 的 `case 'source-settled'`），只有所有组 ready 且为空才收起。
所以**一轮总耗时由最慢的那个源决定**：`settings.get` 慢，整轮就慢，其余源再快也无济于事。

慢在服务端：`index.js:105699` 的 `settings.get` → `settingsView()`（`:106213`）→
`associations()`（`:106233`）→ `association()`（`:106244`），那里每次都要
`IdentityStore.loadExisting()` 与 `ServerCredentialStore.load()`（`:106251-106253`）读凭据文件。

`hostCache`（`:7928`）只缓存 device 对象供 `onPick` 使用，不缓存 `settings.get` 结果，
所以这条路径每次 `@` 都会重新走一遍。

### 结论

**`ds-harness-remote` 让 `@` 菜单从约 180ms 变成约 1.8 秒，是持续阻塞而非偶发尖峰；
并发时还会线性叠加到数秒。**

治本方向（需改 `ds-harness-remote`，不是本仓的包）：把 `settings.get` 结果在客户端侧缓存
（它只在设置页变化时才变），或把 `remoteTools.enabled` 判定挪到装配期一次性读取。

### 当前状态

本机已把 `ds-harness-remote` 置为 `disabled: true`。此前把它归类为「无影响」是**错误的** ——
当时只测了中位数，且很可能是在它尚未生效的窗口里测的。

**方法学教训（新增纪律）：判定插件影响必须看尾部与「每次是否都慢」，
只测中位会漏掉阻塞型问题；对照实验必须确认被测插件当时确实处于生效状态。**

## 最终结论：影响 @ 菜单展现速度的两个层面

口径同场景 E：**从按下 `@` 到候选行出现在界面上**（`role="option"` 由 0 变非空），
不是 RPC 往返、也不是菜单容器出现的时间。下面两项作用于不同层面，分别陈述，不合并归因。

### 一、全局样式的规模（渲染层）

本机 profile 叠加了 62 个插件来源注入的样式：**8853 条规则、215 个 `<style>` 标签合计约 994 KB**
（`document.styleSheets` 计 217 张，比 `<style>` 多出的 2 张来自别的注入方式），其中 29 个含 `html` / `body` 整页选择器。

对照实验保持页面 DOM 与全部插件不变，**只切换样式表的启用状态**，同一操作重复测量：

| 条件 | 菜单展现耗时（5 次） | 中位数 |
|---|---|---|
| 样式表全部启用 | 158.3 / 171.7 / 178.6 / 188.9 / 208.5 ms | **178.6 ms** |
| 样式表全部禁用（DOM 与插件不变） | 47.6 / 48.2 / 52.1 / 61.2 / 68.7 ms | **52.1 ms** |

**同一份 DOM、同一组插件，只是关掉样式表，菜单就快了约 126 ms。** 这排除了「插件逻辑慢」的解释——
慢在样式匹配本身：菜单展开时新增的候选行要参与全量样式计算，规则越多、整页选择器越多，单帧成本越高。

补一组只关大头的对照：只禁用体积最大的两个来源（`dsh-context` 180 KB、`dsh-better-sidebar` 143 KB，
合计 323 KB / 38 张表）后是 133.8 / 152.5 / 163.3 / 181.0 ms，中位数 158 ms ——
比全开（178.6 ms）只低约 20 ms，离全禁用的 52 ms 还很远。

> **治本方向：让 DSH 的客户端插件能把样式隔离到自己的 Shadow root 里。**
> 现在所有插件的 CSS 都注入同一份 `document.head`，谁的规则都参与全页匹配；
> 若插件组件渲染进 Shadow DOM 并用 `adoptedStyleSheets` 挂载样式，样式只在各自的树内参与匹配，
> 全页样式规模随插件数量增长的问题从根上消失。
>
> 目前已验证的现状（`attachShadow` 在 70 个官方客户端包里出现 0 次，`adoptedStyleSheets` 也是 0）：
> 主 shell 不用 Shadow DOM，`attachShadow` 只出现在内嵌 devtools 与 electron preload 中。
> 也就是说技术上插件在自己的 slot 组件里 `attachShadow` 是可行的，缺的是宿主侧的配套：
> ① 主题 token（`--dsw-alias-*`）定义在 light DOM，不会穿透进 shadow root，需要宿主转发或提供一套 shadow 侧的 token；
> ② `shell.overlay` 这类浮层依赖 portal 到 `document.body`，在 shadow root 内会被裁剪，需要配套的浮层容器；
> ③ 现有插件靠 `data-plugin-css` 去重、靠 `document.head` 顺序做覆盖，隔离后彼此不可见，迁移期要允许两种方式共存。
>
> 也就是说，这需要 DSH 在 slot / 样式注入层面提供一等支持（转发 token、给浮层留出口、保留全局样式通道），
> 光靠插件单方面 `attachShadow` 是拿不到的。在这一步做到之前，只能先从「少装往 `head` 塞整页样式的插件」这一步退而求其次。

### 二、远端插件的同步检查（数据层）

`ds-harness-remote` 注册了一个 `trigger: '@'` 的源，其 `candidates` 第一行就
`await control('settings.get')`（`dist/client.js:7935`）。各源是**并发**聚合的
（聚合循环里没有 `await`），菜单等所有源 settle 才收起，所以**一轮的耗时由最慢的那个源决定**。
而这个 `settings.get` 每次都要在服务端重新读凭据文件（`index.js:106244` 一带），没有任何缓存。

运行时启停该插件做对照，两组候选行数完全相同（都是 28 行），唯一变量就是它的启停：

| 条件 | 菜单展现耗时（5 次） | 中位数 |
|---|---|---|
| `ds-harness-remote` 启用 | 1806.1 / 2012.4 / 2376.5 / 1687.8 / 1775.8 ms | **1806 ms** |
| `ds-harness-remote` 禁用 | 178.9 / 175.7 / 225.4 / 161.4 / 210.3 ms | **179 ms** |

**不是偶发尖峰，是每次必慢**：启用状态下 5 次全部落在 1.69–2.38 秒，没有一次接近 180 ms。

它还会随并发叠加——单次 `settings.get` 约 1.1 秒且在宿主侧串行执行，同窗口的 fast-at 请求被排队：

| 同时在飞的 `settings.get` | 期间一次 fast-at 请求的耗时 |
|---|---|
| 1 | 7.1 ms |
| 2 | 5.5 ms |
| 4 | **2797.3 ms** |
| 8 | **9827.5 ms** |

连按几次 `@` 或多处同时取设置，延迟会累积到数秒。

> 治本方向：把 `settings.get` 结果在客户端侧缓存（它只在设置页变化时才变），
> 或把 `remoteTools.enabled` 的判定挪到装配期一次性读取，别放在每次 `@` 的关键路径上。

### 两点如何区分

样式影响的是**菜单渲染一帧的成本**，量级在百毫秒，且对每个已打开的会话持续存在；
remote 影响的是**候选数据到齐的时间**，量级在秒，且随并发放大。两者叠加在同一次操作里，
但机制与观测口径都不同，不能相互折算成「谁占多少」。

## 附：测试环境的第三方插件

性能数据来自一个叠加了 16 个第三方插件的 profile。列出它们是为了让上面的数字**可对照**——
同样的代码在不同插件组合下表现不同，这份清单就是当时的环境。

两列判定口径：

- **私有**：别人在公共渠道**搜不到、也装不到**。看的是实际安装来源，不是作者是谁——
  从私有仓库 `link:` 或私有 git 装的算私有；发布在 npm 公共 registry 或公开 GitHub 仓库的算公开。
- **改 UI / 注入全局样式**：扫描各包客户端代码里 `document.head.appendChild(<style>)` 注入的
  CSS 是否含整页选择器（`html` / `body` / `:root`，含它们开头的后代选择器）。
  **只给自己的组件加局部样式的不算**——几乎所有客户端插件都会注入自己的组件 CSS。
