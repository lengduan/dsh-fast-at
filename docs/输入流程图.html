dsh-fast-at 代码实际执行流程

本页所有节点、判断与回退边都对应 lib/ 下的真实代码，每个框右上角标注 文件:行号。实线为主路径，右侧分支为不满足条件时的去路，虚线蓝边为回退。

零、三层结构总览

一次 @ 击键从装配到渲染，穿过 host 路由与本地索引两层。装配期任一守卫失败即整体不启用，请求期索引不可用即回落客户端快照——两条回退链路都画在右侧。

一、装配期：client.js 的四个前置守卫

插件加载时先做运行时契约探测。四项任一不成立就 console.warn 后 return——不包装任何源，整个插件不启用，@ 回到原生那条较慢的路径。这是刻意的：半启用会让文件候选静默消失，比直接回落更难排查（client.js:671-682 的注释写明了这个取舍）。

二、每次击键：computeCandidates 的完整决策链

这是插件的主战场。除 indexPathCandidates() 里那一次 fetch，其余判定全部同步——所以「不等待磁盘」是结构保证，不是优化出来的结果。

三、host 半：handle() 的四段线性判定

请求内只有 readJson 一处 await；鉴权、方法判定、pathname 解析、404/405 全在它之前同步完成，writeJson 也全同步。

四、sessions-reader.js：索引构建与缓存

索引模型是「内存 + 缓存文件 + 惰性刷新」：query() 同步跑在内存上，建索引与补标题在后台异步。这张图画的是索引数据从磁盘到返回项的流转，以及每一处失败如何降级。

六、画图时发现的三个易错点

① 首次 @ 必然拿不到索引结果。sessions-reader.js:136-141 的 return { ok:false, code:'index-warming' } 在 if (index === undefined) 块内无条件执行——即使 loadFromCache() 刚把索引建好也一样返回 ok:false。真正可用依赖 warmStart() 已在启动阶段跑过（index.js:48）。
② loading 分支是死代码。它在 sessions-reader.js:98 声明，全文没有任何赋值点，:451 的判断恒假。画成「并发加载去重」会与代码不符，所以图 5 里没有这条边。
③ kind 与 child 是两个概念。kind 是磁盘上写死的类别（:249-253）；child 是查询时按 self 现算的「是否我的直接子会话」（:168-169）。别处的子会话 kind==='child' 但 child:false，会被直接丢弃。
源码：lib/client.js（785 行）、lib/index.js（152 行）、lib/sessions-reader.js（848 行）。
