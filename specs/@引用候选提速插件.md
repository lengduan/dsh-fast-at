# @ 引用候选提速插件

版本：v0.5
状态：已实现并验证（会话候选由本地会话索引提供，纯 JS 实现；文件候选仍由插件自取）

## 问题陈述

在 DSH 桌面端（profile `desktop`）的输入框键入 `@`，引用候选菜单骨架 45–58ms 就出现，但**菜单里的内容行要 1.9–2.7 秒**才出现；用 `@` 搜索会话同样约 2 秒。用户原话「我触发@弹框是很快就出现了，但是出现内容用了大概2秒，搜索也是差不多的时间」。

已排除的原因（本轮实测，勿再重复验证）：

- 磁盘与 zstd 不是瓶颈：389 个会话、397 个 `session.v4.jsonl.zstd`（269MB），全量 readdir + 读前 8KB + stat 只要 407ms，60 个文件首帧解码 30ms。
- 前端菜单渲染不是瓶颈：骨架 45ms。
- 主线程渲染不是瓶颈：`@` 期间最大帧间隔 230ms。
- 宿主整体未挂死：`@` 期间注入 `session.phase` 探测，11–23ms 正常返回。
- 单纯并发不排队：8 个并发候选请求不串行；手动「中止+重发」只要 342ms。
- 不是「等待 history 首次 open」：在 history 早已 open 的热会话里按 `@`，`candidates` 仍要 5434ms。

真正成因（已闭合）：`@` 下唯一会跑会话列举的源是内建 `reference`。它调 `remote.sessionReferenceResolver.candidates` → 宿主 `listCandidates()` → `sessionQuery.listSessions()`，这一步在**宿主侧把 CPU/事件循环占满**，同窗口内**完全无关**的请求也被卡住、并在同一毫秒一起释放。实测：`ds-harness-remote/settings.get` 被卡 3813–14494ms、`session.phase` 连发被卡 863–3803ms 后同时放行，而同一接口裸 fetch 只要 15–139ms。即慢的不是接口，是它被调用时并发抢占宿主。

当前 `@` 下**只有 1 个源**（已实测）：按键后菜单 63 个候选的 id 全是 `dsh-slash-option-reference-N`，分组去重结果 `["reference"]`。全客户端扫描中，只有 `dsh-client-ui-reference` 真正调用候选接口；`dsh-api-remotes` 只是命名空间类型装配，`dsh-client-ui-conversation` 只负责渲染已发的引用文本。

## 方案

做一个树外可安装的客户端插件，**原位包装** `@` 源的 `candidates` 方法：遍历 `ctx.inputTriggers` 下所有 `trigger === '@'` 的源，把每个源的 `candidates` 换成「本地快照查询」，原实现不再被调用（不保留默认回落）。

数据源**不发任何请求**。

> **v0.5 变更**：会话候选已改由 **本地会话索引**提供（见文末变更记录；v0.6 起由 Python 之外的纯 JS 实现，已移除 Rust），本段描述的是**回退路径**——索引不可用时用客户端已有的会话快照 `sessions.list.getSnapshot().byId`（`dsh-better-at` 已用同一手法，`lib/client.js:748-755`）。两种情况都既不触发 `listSessions`，也不引入新的慢接口。

骨架取自 `dsh-better-at` 已验证跑通的形式：包装实例方法 + 劫持 `registerSource` 兜住后注册的源 + `ctx.effect` 登记完整还原的 disposer。区别在于**不保留回落**——用户明确要求「一点都不要走」。

## 用户故事

1. 作为用户，我键入 `@` 后希望 300ms 内看到候选内容行，而不是等 2 秒。
2. 作为用户，我希望 `@` 期间别的请求（用量统计、会话轮询）不被拖慢到秒级。
3. 作为用户，我希望插件卸载后 `@` 完全回到原生行为，不留残留。
4. 作为维护者，我希望插件失效时是「候选变少」而不是「菜单打不开」。

## 实现决策

### 包装点

- 只替换 `candidates(session, req)` 这一个方法。**不碰** `name` / `trigger` / `order` / `header` / `lexicon` / `warm` / `codec` / `onPick` / `openReference`。
- 不新注册源：不新注册就不存在 `(trigger, name)` 唯一性冲突（注册表在重复时会直接 throw）。
- **遍历所有「真正提供候选」的 `trigger === '@'` 源，不硬编码 `name === 'reference'`**。理由：以后装了别的「会拉慢候选」的 `@` 源插件时，硬编码会漏包它。`dsh-better-at` 硬编码 `name === 'reference'`（`lib/client.js:814`）是它自身的隐患。
- **排除「纯回显源」**：`@` 下并非每个源都提供候选，有的源只为渲染已插入的 chip 而注册。实测本机 `dsh-better-sidebar` 注册了 `trigger: '@'` / `name: 'betterSidebarQuote'`，它的 `candidates` 恒返回 `[]`、`onPick` 恒返回 `'handled'`（`lib/client.js:36226-36227`），`codec` 负责把 chip 的 ref 还原成引用文本。这类源**没有候选可提速**，包装它反而会把 `@` 菜单多出一个不该有的分组，且由于 `onPick` 的语义与 `reference` 不同，选中后只能退化成纯文本——属于功能破坏。
- **判据要保守**：只有当源「确实会产出候选」时才包装。做法是**首次调用前不预测**，而是按「该源当前是否已在菜单里产出过行」不足以判断（菜单未打开时无法得知），因此采用**显式豁免名单 + 保守探测**：
- 显式豁免：`name` 在 `NON_CANDIDATE_SOURCES`（当前为 `['betterSidebarQuote', '主机']`）里时不包装。
  - `betterSidebarQuote`（`dsh-better-sidebar`）：纯回显源，`candidates` 恒 `[]`、`onPick` 恒 `'handled'`。
  - `主机`（`ds-harness-remote`，`dist/client.js:7920-7939`）：`candidates` 返回**在线远程设备**，`onPick` 返回 `{ text: '@设备名 (Remote hostId=…)' }`。包装它会把设备分组换成会话/文件行，选中后仍按设备语义拼文本，往草稿插进 `@… (Remote hostId=undefined)` 垃圾——真机已复现。
  - 保守探测：包装时保留原 `candidates` 的**空结果语义**——若原实现的候选在「空 query」下恒为空且 `onPick` 返回非 `insert` 的常量（`'handled'`），说明它是回显源。运行期无法廉价判定，所以只用豁免名单，并在 README 里写明「新增会拉慢的 `@` 源需手动加入名单」的维护约定。
- 补注册路径：劫持 `inputTriggers.registerSource`，对晚注册的 `@` 源同样包装；disposer 里还原。

### 为什么不改注册表、不禁用内建插件

`dsh-client-ui-reference` 除 `@` 源外，还注册了 `fileReferenceRule` / `folderReferenceRule`（聊天记录里已发引用的文本渲染）与 `conversation.user.text.node` 插槽。禁用整个插件会让历史消息里的 `@` 引用退化成裸文本。包装实例方法可以只影响候选发现，不动渲染。

### 引用 URI 编码（已取证）

宿主返回的 `mention` 形如 `@[显示标题](dsh-session:<base64url>)`。已取 3 条真实样本并解码验证：**base64url 的明文就是 `JSON.stringify(sessionId)`（即带双引号的 `"<sessionId>"`，UTF-8）**，三条全部精确匹配。

注意是 **base64url 而不是标准 base64**（权威实现在 `dsh-session-reference/src/uri.ts` 的 `encodeSessionReferenceUri`）：字符集只有 `[A-Za-z0-9_-]`，没有尾部 `=`；解码端 `decodeSessionReferenceUri` 还会做 canonical 校验（重编码必须等于原值），所以编码必须严格一致，任何 `+` / `/` / `=` 都会让引用失效。

推论：插件可以自己编码 mention，无需任何宿主调用。规则为 `@[${转义后的显示标题}](dsh-session:${base64url(JSON.stringify(sessionId))})`，其中标题按 `label.replace(/[\\\]]/gu, m => '\\' + m)` 转义 `\` 与 `]`。这条原本被列为技术死穴，现已消除。

浏览器半不能 import `@deepseek-ai/dsh-session-reference`（profile 的 `node_modules` 里没有该包），因此 base64url 用 `btoa` + `TextEncoder` 本地复刻。

### 数据源

- **首选本地会话索引**（v0.5 起，v0.6 改为纯 JS）：全量数百个会话，按文件 mtime 倒序，纯内存查询 0.014–0.057ms。
- **回退** `sessions.list.getSnapshot().byId`：零请求、同步可得；只在本地索引不可用时使用。
- 字段来自客户端快照，不保证与宿主 `listCandidates` 完全等价：缺 `sameWorkspace` 时可由 `cwd` 与当前会话 `cwd` 比较补算；`displayTitle` 缺失时回落 `label`。
- 候选行的 `value` 字段必须与原生同构，且**它是 JSON 字符串而不是对象**：`JSON.stringify({ kind: 'session', label, mention })`。原生的 `onPick` 对 `candidate.value` 做 `JSON.parse` 后按 `kind` 分派（`file` / `session`），所以给对象会让 `JSON.parse` 抛错、点选失效。

### 文件候选由插件自取（决策：保留，不跟着一起消失）

原生的 `reference` 源在一次 `candidates` 调用里**并行**跑两件事：`fileReferences.list`（文件与文件夹候选，实测 15ms）和 `sessionReferenceResolver.candidates`（会话候选，1.9–2.7 秒的元凶）。本插件把这**整个** `candidates` 方法替换掉，所以原函数体整段不再执行——**文件候选也会跟着一起消失**。用户的 `@ 文件名` 将没有任何结果，属功能回退，不接受。

因此插件内部自己调一条 `ctx.remote.fileReferences.list(session.sessionId, query, signal)`，把文件候选按原生语义拼回去：

> **依赖声明（v0.4 订正）**：`remote` 与 `remote.fileReferences` 必须写进插件的 `inject`，与原生 `ui-reference` 完全一致（`src/client/index.ts:46-49` 声明 `'remote', 'remote.fileReferences'`）。
> 早期实现把 `remote` 当「可选依赖」、只用 `ctx.get('remote')` 取，实测结果是**文件候选全部消失**——`ctx.get('remote')` 返回不到那个命名空间时插件退化成 `remote = {}`，`fileReferences.list` 永远不可用，而失败又被 catch 成空数组，界面上表现为「文件候选静默消失」，非常难查。
> 教训：文件候选是本插件的功能契约（用户明确要求保留），提供它的依赖就不是可选的。

- 这条请求只要 15ms，**不触发** `sessionQuery.listSessions`，不引入 2 秒问题，也不违背「绕开 listSessions」的初衷。
- 它是 `@` 下唯一额外引入的请求；除它之外插件不发任何请求。
- 失败一律 `.catch` 成空数组（与原生 `result.ok ? result.value : []` 等价），不允许因文件侧失败把会话行也拖没。

**必须复刻的原生文件候选语义**（权威：`dsh-client-ui-reference/src/client/index.ts` 的 `fileCandidate` 与 `dsh-file-reference/src/grammar.ts` 的 `formatFileMention`）：

| 项 | 规则 |
|---|---|
| mention 拼装 | 目录先把 `path` 补尾斜杠；路径含 `[\u0000-\u001f\u007f-\u009f"]` 时**丢弃该行**；`preserveQuote`（即 `quoted === true`）或路径含空白时加引号：文件 `@"path"`（闭合），目录 `@"path/`（**开引号不闭合**）；否则 `@path` / `@path/` |
| `value` | JSON 字符串 `JSON.stringify({ kind: 'file', fileKind, label: name, mention })` |
| `name` | 路径最后一段；目录再加 `/` |
| `description` | 仅当 `withLocation` 为真且父目录非空时填父目录 |
| `icon` | 目录 `'folder'`，文件 `'file'` |
| `drill` | 目录行 `drill: true`；文件行不设 |
| `section` | 文件分组标题；与原生同一本地化键 |
| 顺序 | 文件行在最前，然后是「当前会话的直接子智能体」，最后是其它会话 |

`withLocation` 必须与原生同一判据（因为 `header` 方法不接管、面包屑仍由原生提供）：`drilled` 为假，或 query 里没有 `/` 时才有位置需要行自己承载。两者用同一条件，才能保证「有面包屑时不重复父目录、没面包屑时行自带父目录」自洽。

`formatFileMention` **必须本地复刻**：浏览器半不能 import `@deepseek-ai/*`（profile 的 `node_modules` 里没有这些包，实测 `ERR_MODULE_NOT_FOUND`），只能按上面规则用纯 JS 重写，并由验收脚本用表驱动用例逐分支锁死。

**不碰 `header`**：drill 之后的面包屑仍由原生 `header` 方法产生，插件不实现也不接管它。

### 性能措施

- 自带防抖与缓存：`controller.ts` 每次击键都会 abort 上一轮并重发，无防抖。插件侧按 `query` 做内存缓存，避免重复计算。
- 尊重传入的 `signal`：abort 后不得再提交结果，否则旧 generation 的结果会覆盖新结果（`menu.ts:114` 按 generation 丢弃，处理不当表现为候选闪一下就没）。
- 结果截断：对话展示上限 `CANDIDATE_LIMIT = 20`、子对话 `CHILD_LIMIT = 10`（见「候选分组与上限」）。**注意区分「索引规模」与「展示上限」**：本地索引装的是**全量 header**，过滤在内存里对全量做，最后才按上限截断展示。所以老会话能被搜到，不受展示上限影响。

### 会话扫描（v0.5 新增，v0.6 改为纯 JS）

会话候选的数据源从「客户端快照」升级为**本地磁盘索引**，理由是快照只含「侧栏已加载」的会话，而磁盘上有全量数百个。

`dsh-fast-at/lib/sessions-reader.js`（纯 JS，用 `node:zlib` 的 `zstdDecompressSync`）做三件事：

1. **扫 header**：遍历 `~/.dsh/sessions/<project>/<uuid>/session[.vN].jsonl.zstd`，只解**第一帧**取 header（实测第一帧 max 245 字节，不必读最大 782KB 的整个文件）。
2. **排序**：按会话文件 `mtime` 降序（见下节）。
3. **补标题**（v0.8 起，用户 2026-11-26 定）：**对话全量补**，**子对话只补当前会话的**，
   且补到的标题**落盘**，之后重建直接沿用、只判断不解盘。

标题策略演进与实测（本机 324 个会话）：

| 版本 | 策略 | 重建耗时 |
|---|---|---|
| v0.5 | 只补 mtime 前 30 条 | 328–630ms |
| v0.8 | 对话全量（176 个）+ 当前会话子对话 | **1324–1547ms** |
| v0.8 稳态 | 全部命中缓存 | **648ms** |

**为什么改成对话全量补**：只补前 30 条时，掉出预算的会话在 `@` 里回落成 `session-xxxx` 原始 id，
按 id 搜到也看不出是什么。用户要求「只全量补对话的会话」，代价 663ms 全在后台异步，
`@` 响应不受影响（纯内存 0.03–0.08ms）。

**为什么子对话只补当前会话的**：148 个子对话里有 139 个属于别的会话，为它们解盘是纯浪费。
当前会话的子对话在 `query()` 时才知道，所以那部分在 `@` 时补。

**为什么补过就不用再补**：子对话标题**不会变化**（用户在创建时命名），
所以补到即写回缓存文件，下次重建走 `readCacheLabels()` 直接继承——
实测稳态 `@` 只剩 0.18–0.73ms 的判断开销。

**标题取值优先级**（v0.8 修正）：`subagent/descriptor.label` > `session/title`。
先前的实现只读 `session/title`，子会话拿到的是 `source.kind = "fallback"` 的
**首条消息截断**（如「你是独立复核者。任务：复核」），与界面顶部子智能体面板显示的真名
（「复核搜索排序耗时结论A」）不一致。descriptor 恒在第 1 帧，优先读它不增加解压量。

**索引在后台建一次（实测中位数 328ms），`@` 时是纯内存查询（实测中位数 0.027ms）**：
启动后异步 spawn 一次，结果进内存；索引超 30s 后台刷新，**永不阻塞 `@`**（stale-while-revalidate）。

> 为什么不能每次 `@` 都 spawn：Windows 下 387 个目录 ×（三次 `readdir` + 一次 `stat`）的固有成本就接近 200ms，加解压实测中位数 328ms。物理上无法**稳定**满足 300ms 判据（采样波动到 397ms）。索引模型让**用户感知延迟与索引构建耗时解耦**。

### 候选分组与上限（v0.8 新增）

用户 2026-11-26 定的口径：

| 组 | 内容 | 上限 |
|---|---|---|
| 子智能体 | **仅当前会话的直接子会话** | **10** |
| 对话 | 仅普通会话，**任何子会话都不进** | 20 |

两组**各自独立计数**互不挤占（旧实现是混合截断，子智能体一多就把对话整体挤掉）。

- 「没给 self 就不分组」：不传 self 时原样返回（全量核对用），不套用上面的过滤。
- **别处的子会话两侧都不出现**：既不在「子智能体」组（不是当前会话的子），
  也不在「对话」组（对话只放普通会话）。实测当前会话有 9 个子对话、139 个别处的子对话，
  只有那 9 个出现在「子智能体」组，「对话」组混入 0 个。
- 分组依据是**磁盘索引里的 `kind` 标记**（`chat` / `child`），不是每次现算 origin。

> 子对话上限 10 的理由（用户原话）：「子对话一般来说都不多，20 条太浪费了」。
> 客户端快照回退路径（`client.js`）用同一个常量，主路径由宿主 `CHILD_LIMIT` 截断。

### @ 时补子对话标题（v0.8 新增）

`@` 触发时若发现**本次要返回的**子对话缺标题，**同步**补上并写回缓存：

- 只处理**本次返回的这几条**（受 `CHILD_LIMIT` = 10 约束），实测 9 条约 7–14ms。
- **不做异步补其余**（用户明确要求去掉）：「你是在返回后才做的标题更新，时机上已经受到
  limit=10 的限制，这里只保留标题缺失检查读取写回缓存的逻辑，不做异步更新了」。
- 补到就 `persistLabels()` 异步写盘。不写回的话每 30 秒重建一次就要重解一遍，等于白补。
- 缓存里**必须存 `path`**：补标题要定位文件。早期版本没写这个字段，
  从缓存加载后无从下手，补标题会静默跳过、永不生效。

实测：抹掉 9 条标题后第 1 次 `@` 13.9ms 补全并落盘，第 2 次 0.97ms，稳态 0.18–0.73ms。

### 排序（v0.5 新增）

用户明确要求「按照文件修改时间排序取最新的 20 条」，因此：

- **主键：会话文件 `mtime` 降序**。
- 次级键：`candidateRank` 升序（0 同工作区 / 1 无 cwd / 2 其它），用于同 mtime 时让同工作区的会话靠前。
- 末级键：`sessionId` 字典序，保证结果稳定可复现。

注意这与原生 `listCandidates` 的排序（`candidateRank` 优先）**不同**，是本轮按用户显式要求做的偏离。

### 会话 id 的两种写法（v0.5 新增）

磁盘上的会话 id 有两种合法形态：`<uuid>` 与 `session-<uuid>`，实测两种混用（v0.8 采样 176 带前缀）。同一条「父—子」关系里两侧写法可能不同。

因此**比较 id 时必须归一化**（去掉 `session-` 前缀），否则会静默失配，表现为「子智能体分组消失」或「排除不掉当前会话」。归一化只用于比较，**返回给前端的 `sessionId` 保持原样**——mention 解码依赖原始值。

### 失败与还原

- **三级降级（v0.5 修正）**：`T1 本地索引 → T2 客户端快照 → T3 空数组`。任何情况都**禁止回落原生** `candidates`（那会重新引入 2 秒等待），但**允许**回退到本插件自己的客户端快照实现。
  - 理由：决策 4 的原意是「不许回落原生 2 秒」，不是「不许任何兜底」。索引带来几类新失败面（目录不可读、zstd 帧损坏、header JSON 非法、磁盘异常），返空会让用户**彻底失去 `@` 会话能力**，比原生慢 2 秒更糟；而快照回落是零请求的现有代码。
  - 实现落点：`client.js` 的 `(await indexPathCandidates(...)) ?? sessionCandidates(...)`。
- 所有包装都经 `ctx.effect` 登记还原：卸载时把 `candidates` 与 `registerSource` 改回原值，并清掉自定义标记位。
- 版本探测：依赖 asar 内的私有实现（`live.sources` 是 TS private 字段、`ctx.remote` 命名空间、引用 URI 编码），升级后若探测失败则不启用包装并记录日志，不抛错。

## 已决事项（原「待定项」，逐条给出决策与验收落点）

1. **客户端快照的完整性 → 按 `byId` 即全集处理。** 宿主 `apiSessionList.list()` 直接遍历 `sessionQuery.listSessions()`，链路里**没有**归档过滤（`archived-session-gate` 只拦 `agent/pre-step`，不拦列表），列表本身也是全工作区的；客户端 `projectList()` 在此基础上再补 retained subagent 兜底行。因此 `byId` 覆盖「会话列表能看到的全部会话」，与原生的会话候选同源，不是回归。字段缺口用补算填：`sameWorkspace = summary.cwd === 当前会话 cwd`；`createdAt` 不用（原生只在列表缺失该会话时回落它，而插件只从快照出候选，不存在这种缺失）；`label` 用 `displayTitle`；**必须排除当前会话自身**（原生 `listCandidates` 就排除）。实测判据见「校验与验收」第 1 条与施工方案 A1。

2. **文件候选 → 保留，由插件自取**（见「实现决策 · 文件候选由插件自取」）。原「默认不拦」的理由「风险大」已被用户否决：不保留会让 `@ 文件名` 完全没结果。多引入的那条请求是快的那个（15ms），不触发 `listSessions`。验收要求文件候选在装/卸两态**逐字段等价**。

3. **`@` token 形态敏感 → 已定位为「query 无结果 / 输入相 guard / dismiss 粘滞」，插件侧不复刻 token 规则。** `activeAtToken` 的正则是 `/(?:^|\s)(@([^\s]*))$/`，`@@@` 的 query 会是 `@@`，**能匹配**；所以「连按 @@@ 后内容不出」不是检测规则失败。更可能的原因是：query 变成 `@@` 后文件/会话都无结果 → 空组自动关闭（菜单自己消失，看起来像「没反应」）；或输入相为 `claimed`/`frozen` 时 `detectTrigger` 直接返回 null；或同一 token 位置被 `dismissed` 记录后不再重开。**插件不需要任何处理**：它拿到的 `req.query` 已经是宿主算好的，插件只按 query 做本地过滤。复现与归因步骤见施工方案 B-3 / 验收 A4。

4. **冷启动 → `phase` 非 `ready` 时返回空数组，不等待、不预热。** 实测 `SessionListPhase` 只有 `'pending' | 'ready'` 两个值（不存在 `'empty'`；「真的没有会话」表示为 `phase === 'ready' && ids.length === 0`）。页面刚加载、首个列表 pull 尚未落地时 `byId` 为空，此时返回空数组让菜单自动关闭，与原生在同等条件下的表现一致，只是不用等 2 秒。**不做预热**：预热等于主动发请求，触碰的正是要绕开的那条链路。**不做等待**：`candidates` 的 `signal` 每次击键都会 abort，等了也白等，还把「骨架闪一下」变成「骨架停 2 秒」。行为矩阵见施工方案 B-4 / 验收 A5。

### 为什么不能每次 @ 都 spawn（实测数据）

| 做法 | 耗时 |
|---|---|
| 纯目录遍历 + stat（不含解压，Node 对照） | 177–268ms |
| Rust 全量扫 header（`--no-titles`） | 558–806ms |
| Rust 完整（含 20 条标题，**加 --title-limit 之前的旧实现**） | 1187–2135ms |

Windows 下 387 个目录 ×（三次 `readdir` + 一次 `stat`）的固有成本已接近 200ms，
所以「每次 @ 都调 Rust」物理上无法满足 300ms 判据。改为**索引模型**：
索引在后台建好（慢一次），@ 时纯内存查询（0 I/O）。**用户感知延迟与 Rust 扫描耗时解耦。**

### frameEnd 的坑（写进规格避免重踩）

多帧 zstd 必须按帧头结构步进，不能靠 magic 扫描（压缩正文里会出现伪 magic）。最易错的一行：

```js
// 错：fcsFlag=0 且 singleSegment 时漏掉那 1 字节 → 103/398 个大文件解析失败
contentSizeBytes = [singleSegment ? 0 : 1, 2, 4, 8][fcsFlag]
// 对：
contentSizeBytes = fcsFlag === 0 ? (singleSegment ? 1 : 0) : 1 << fcsFlag
```

另一个坑：`zlib.zstdDecompressSync(整个文件)` **只解第一帧**，不是全部——用它读标题会得到「很快但命中 0」的假结果。
